# Как внести вклад в hiiire

Спасибо, что хотите помочь проекту. Ниже — всё, что нужно, чтобы поднять проект локально и отправить изменения.

## Прежде чем начать

- Для заметных изменений (новая фича, изменение схемы БД, публичного API или поведения биллинга) сначала откройте issue и опишите идею. Так мы договоримся о подходе до того, как вы потратите время на код.
- Мелкие исправления (опечатки, баги с понятным воспроизведением, тесты) можно присылать сразу pull request'ом.
- Уязвимости не публикуйте в issues — см. [SECURITY.md](./SECURITY.md).

## Локальный запуск

Требования: Node.js `>= 20.9` (проверено на `22.17`), npm `>= 10`, отдельный Supabase-проект для разработки (облачный или self-hosted).

```bash
npm ci
cp .env.example .env.local   # заполните значения своего dev-окружения
npm run dev                  # http://localhost:3000
```

- Схема БД для пустого проекта собирается из `supabase/migrations/` — порядок и детали в [`supabase/bootstrap/README.md`](./supabase/bootstrap/README.md).
- Фоновая обработка AI-задач — отдельный процесс: `npm run worker:build && npm run worker:start`.
- Интеграции (HH.ru, AI-провайдеры, Telegram, Robokassa, Tika, PostHog) необязательны для старта: без ключей соответствующие функции просто недоступны. Полный список переменных — в [`.env.example`](./.env.example), подробности — в [README](./README.md) и [DEPLOYMENT.md](./DEPLOYMENT.md).
- Никогда не подключайте локальную сборку к чужой production-базе и не коммитьте `.env*` с реальными значениями.

## Ветки и pull request'ы

- Базовая ветка для разработки — `dev`. Создавайте ветку от актуального `dev` и открывайте PR в `dev`; `main` обновляется релизными PR из `dev`.
- Именование веток: `feat/...`, `fix/...`, `docs/...`, `chore/...`.
- Один PR — одна логическая задача. В описании укажите, что изменилось, зачем и как вы это проверили.

## Проверки перед PR

```bash
npm run lint
node --no-warnings --experimental-strip-types --test tests/*.test.mts   # или точечный npm run test:*
npm run build
```

Если меняли worker, Telegram relay или Tika proxy, прогоните их сборку и тесты (`npm run worker:selfcheck:build`, `npm run telegram-relay:test`, `npm --prefix tika-proxy test`).

## Правила кода

Проект работает в продакшене, поэтому изменения оцениваются как production-код, а не прототип.

- **Пограничные случаи.** Продумайте пустые и частично заполненные состояния, ошибки сети и API, повторные клики, гонки запросов, ограничения доступа, длинный ввод и узкие экраны.
- **Тексты в интерфейсе** пишутся для конечного пользователя: коротко, по-русски, с понятным следующим шагом. Никаких raw-кодов ошибок, stack trace и технических формулировок.
- **API и формы:**
  - ошибки валидации возвращаются как `400` в формате `{ error, message?, issues? }`, где `message` безопасен для показа пользователю;
  - Zod-схемы пользовательских полей содержат явные русские сообщения;
  - клиент зеркалирует серверные лимиты (`maxLength`, inline-валидация);
  - ошибки API разбираются общим helper'ом проекта, а не локальным `throw new Error(json.error)`.
- **Вёрстка:** длинный пользовательский текст защищается через `min-w-0` / `truncate` / `break-words`; повторяющиеся дефекты UI исправляются в примитивах `components/ui/*`.
- **База данных:** изменения схемы — только новой миграцией в `supabase/migrations/` (уже применённые миграции не редактируются), с обновлением [`docs/DATABASE_SCHEMA.md`](./docs/DATABASE_SCHEMA.md) и типов `lib/supabase/database.types.ts`.
- **Документация:** если изменилось поведение, API, конфигурация или переменные окружения, обновите `README.md` / `DEPLOYMENT.md` / `.env.example`. Пользовательские сценарии для ручного QA описываются в [`docs/For_juniors/hiiire_for_junior.md`](./docs/For_juniors/hiiire_for_junior.md) языком видимого UI, URL и HTTP-статусов, без ссылок на внутренние функции.
